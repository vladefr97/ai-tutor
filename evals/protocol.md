# Протокол проверки качества оценивания

Статус: зафиксирован 28 октября 2026 года, до первого прогона `make eval-live`. Основание: AC-10 в [приёмке](../docs/poc-acceptance.md), issue #10 и #23.

Протокол измеряет, насколько Ревьюер работ правильно выносит вердикт «зачёт» или «нужны исправления». Он не измеряет пользу обучения и качество сгенерированных материалов.

## Что оценивается

| Объект | Как проверяется | Входит в метрики качества |
|---|---|---|
| Выбор одного и нескольких ответов | Детерминированное сравнение набора на сервере; модульные тесты | Нет, модель не участвует |
| Короткий ответ встроенного вопроса (Python, Git, PM) | Ревьюер работ направления | Да |
| Практический кейс PM, включая экзаменационный с изменением условий | Ревьюер работ PM | Да |
| Код Python и Git в pull request | Официальные проверки и Ревьюер работ направления | Да |

Ревьюер плана и ревью сгенерированных заданий до публикации этим протоколом не измеряются.

## Структура набора

Путь случая: `evals/cases/<direction>/<kind>/<case-id>.json`.

- `direction`: `python`, `git`, `pm`.
- `kind`: `short_answer`, `case` (только `pm`), `code` (только `python` и `git`).

Поля случая:

```json
{
  "id": "python-short-007",
  "direction": "python",
  "kind": "short_answer",
  "task": "Зачем функции нужен return?",
  "criteria": [
    "1. Указано, что return возвращает значение вызывающему коду",
    "2. Указано, что выполнение функции на return завершается"
  ],
  "reference": "return передаёт значение туда, где функцию вызвали, и сразу завершает функцию.",
  "answer": "Функция отдаёт результат тому, кто её вызвал, и дальше не выполняется.",
  "class": "alternative_correct",
  "expected": "pass",
  "rationale": "Выполнены критерии 1 и 2 другими словами",
  "mutation": "paraphrase",
  "forbidden": [],
  "source": "agent-config/directions/python/criteria.md#functions"
}
```

- `class`: `correct`, `alternative_correct`, `incomplete`, `incorrect`.
- `expected`: `pass` для `correct` и `alternative_correct`, `changes_requested` для `incomplete` и `incorrect`. Других сочетаний нет.
- `rationale`: ссылается на номера критериев, а не на мнение модели.
- `source`: файл экспертной основы, из которого взяты задание и критерии.
- `forbidden`: фрагменты эталонного решения, которых не должно быть в замечаниях (см. «Утечка решения»).
- Для `code` вместо `answer` указывается `solution_dir` с файлами решения и `diff`; `reference` указывает на эталонное решение, `checks` на официальные тесты задания.

Минимальный объём на каждую пару «направление × вид»: 8 случаев, по 2 на каждый класс. Пар шесть: `python/short_answer`, `git/short_answer`, `pm/short_answer`, `pm/case`, `python/code`, `git/code`, итого не меньше 48 случаев. Набор можно расширять до прогона; после первого прогона версия набора фиксируется в отчёте.

## Происхождение ожидаемых результатов

Ожидаемый вердикт выводится из критериев и способа построения ответа. Вывод любой модели, в том числе другого агента, не используется как ожидание.

Текстовые случаи строятся от эталона, который выполняет все критерии:

| Мутация | Класс | Ожидание |
|---|---|---|
| Эталон без изменений | `correct` | `pass` |
| Перефраз эталона без потери критериев, другие термины, другой порядок | `alternative_correct` | `pass` |
| Удалён элемент, покрывающий хотя бы один критерий | `incomplete` | `changes_requested` |
| Искажён факт, требуемый критерием, или добавлено ложное утверждение | `incorrect` | `changes_requested` |

Текст случаев может предложить модель, но класс и ожидание задаёт мутация, а `rationale` проверяется по номерам критериев. Случай, где мутация не меняет выполнение критерия, исправляется или удаляется до прогона.

Для кода ожидание задаётся исполнением:

- Официальные тесты запускаются на решении случая. Решение класса `correct` или `alternative_correct` обязано их пройти, `incorrect` обязано упасть. Иначе случай невалиден.
- `incomplete` для кода: официальные тесты проходят, но нарушен проверяемый критерий ревью (например, не обработан описанный в задании крайний случай, который тестами не покрыт, или нарушено явное требование к структуре). Нарушенный критерий указывается в `rationale`.
- `alternative_correct` для кода: другой алгоритм или структура, тесты проходят, все критерии выполнены.
- Ожидаемый вердикт ревьюера кода: `approve` только для `correct` и `alternative_correct`. Approve при упавших официальных проверках считается ложным зачётом независимо от класса.

Человеческая разметка пользователем не требуется. Агент-разработчик собирает случаи по правилам выше, валидатор набора проверяет поля, сочетание класса и ожидания и, для кода, результат официальных тестов.

## Метрики

Считаются по каждой паре «направление × вид» и по направлению в целом.

- **Ложный зачёт (FA)**: доля случаев `incorrect` и `incomplete`, получивших `pass` или `approve`.
- **Ложный отказ (FR)**: доля случаев `correct` и `alternative_correct`, получивших `changes_requested`.
- **FR на перефразе**: FR только по `alternative_correct`; показывает, оценивает ли ревьюер смысл, а не совпадение с образцом.
- **Утечка решения**: число вердиктов, где замечания содержат готовое решение. Детектируется автоматически: совпадение с фрагментом из `forbidden`, для кода блок кода длиннее 3 строк, совпадающий с эталоном после нормализации пробелов. Проверка консервативная: срабатывание считается утечкой.
- **Ошибки провайдера**: тайм-аут, ошибка API, ответ, не прошедший схему `contracts/agent-result.schema.json`. Такой вызов получает статус `error`, не входит ни в FA, ни в FR и никогда не превращается в зачёт.
- **Нестабильность**: доля случаев, где три повторных вердикта не совпали.

## Пороги

Зафиксированы до прогонов и не меняются задним числом.

| Метрика | Порог | Уровень |
|---|---|---|
| FA | ≤ 5 % | каждое направление, каждая пара |
| FR | ≤ 15 % | каждое направление |
| FR на перефразе | ≤ 25 % | каждое направление |
| Утечка решения | 0 | весь набор |
| Ошибки провайдера | ≤ 5 % вызовов | весь прогон, иначе прогон недействителен |
| Нестабильность | ≤ 15 % | весь набор |

Ложный зачёт хуже ложного отказа. Зачёт без знаний разрушает смысл курса и экзамена, и ученик о нём не узнает. Ложный отказ ученик видит в замечаниях, может исправить ответ или спросить Наставника, поэтому порог FR мягче. Утечка решения прямо запрещена приёмкой, отсюда ноль.

При 8 случаях на пару одна ошибка уже даёт 25 % на классе. Поэтому порог FA на паре при минимальном наборе фактически означает «ни одного ложного зачёта», а FR оценивается по направлению, где случаев больше.

## Повторяемость

- Каждый случай прогоняется 3 раза в независимых запросах без общего контекста.
- Итоговый вердикт случая выбирается по большинству из вердиктов без ошибок. Если валидных вердиктов меньше двух или они разошлись 1:1, случай получает `error`.
- Нестабильность считается до агрегации.
- В отчёте фиксируются модель и её версия, параметры запроса (temperature, reasoning effort, если поддерживается), версия Codex, хеш SHA-256 каждого использованного промпта и файла критериев, коммит репозитория и версия набора.

## Команды

`make test-assessment`: детерминированные проверки без сети.

- Сравнение наборов выбора одного и нескольких ответов.
- Логика оценивания на фиксированных ответах модели: правильный разбор вердикта, отказ при невалидном ответе, тайм-аут и ошибка дают `error`, approve при красной официальной проверке отклоняется.
- Валидатор набора: поля, сочетание класса и ожидания, минимальные объёмы, исполнение официальных тестов на решениях случаев `code`.
- Расчёт метрик и сравнение с порогами на заранее известных вердиктах.

`make eval-live`: реальные вызовы Ревьюеров работ.

- Требует ключ API в окружении; без ключа завершается ошибкой, а не пропуском.
- Прогоняет весь набор по правилам повторяемости, считает метрики, пишет отчёт и возвращает ненулевой код, если нарушен хотя бы один порог или прогон недействителен.

## Отчёт

Путь: `evals/reports/<YYYY-MM-DD>-<model>.json` и рядом `.md` со сводкой.

JSON содержит:

- среду: модель, параметры, версия Codex, коммит, версия набора, хеши промптов и критериев;
- по каждому случаю: входы (задание, критерии, ответ или diff), ожидание, три фактических вердикта с замечаниями, итог, ошибки;
- метрики по парам и направлениям, результат сравнения с порогами;
- ограничения прогона.

Ключи, токены и заголовки авторизации в отчёт не пишутся. Перед записью отчёт проверяется на совпадение со значениями секретов из окружения.

Сводка `.md`: таблица метрик против порогов, список ложных зачётов и утечек с id случаев, итог «пройден» или «не пройден».

## Правила при непрохождении

- Исправляется система: промпты Ревьюера работ, формулировки критериев в экспертной основе, разбор ответа модели, выбор модели.
- Пороги и уже прогнанные случаи не меняются. Невалидный случай можно исключить только с записью причины в отчёте следующего прогона, и только если ошибка в самом случае доказана правилами из раздела «Происхождение ожидаемых результатов», а не вердиктом модели.
- Каждый повторный прогон сохраняется отдельным отчётом; прежние отчёты не удаляются и не перезаписываются. Если в один день прогонов несколько, к имени добавляется суффикс `-2`, `-3`.

## Ограничения методики

- Ответы синтетические и построены мутациями эталона. Реальные ответы учеников разнообразнее и могут давать другие ошибки ревьюера.
- Ожидания опираются на критерии, созданные тем же процессом, что и курс. Протокол измеряет согласие ревьюера с критериями, а не качество самих критериев.
- Минимальный набор мал; пройденные пороги не являются статистическим доказательством, а показывают отсутствие грубых сбоев.
- Детектор утечки решения ловит буквальные совпадения и может пропустить пересказ решения словами.
- Для кода класс `incomplete` ограничен критериями, которые не покрыты официальными тестами; их немного.
- Результаты относятся к зафиксированной модели и версиям промптов; смена любой из них требует нового прогона.
