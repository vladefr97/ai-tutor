# Экспертная основа: Git

Направление «Наставник по Git» учит вести историю изменений проекта и работать с удалённым репозиторием и pull request так, как это делают в команде. Ученик — новичок или человек, который пользуется Git «по шпаргалке». Практика — задания в личном учебном репозитории на GitHub; официальные проверки читают историю Git клона ученика.

## Границы

Входит:

- установка Git, настройка `user.name` и `user.email`, работа в терминале (`cd`, `ls`) на уровне, нужном для Git;
- локальный репозиторий: `init`, `status`, `add`, `commit`, `log`, `diff`, рабочая копия, индекс и история;
- хорошие коммиты: небольшие логичные изменения и понятные сообщения;
- `.gitignore`: что не коммитить и почему;
- ветки: `branch`, `switch`/`checkout`, `merge`, fast-forward и merge-коммит;
- конфликты слияния: как возникают, как читать маркеры, как разрешить и закоммитить;
- откат изменений: `restore`, `reset` (мягкий и смешанный), `revert`, `commit --amend` для последнего неопубликованного коммита; чем опасно переписывать опубликованную историю;
- удалённый репозиторий: `clone`, `remote`, `fetch`, `pull`, `push`, отслеживание веток;
- pull request на GitHub: ветка, push, создание PR, ответ на ревью новыми коммитами, слияние;
- чтение истории: `log --oneline --graph`, `show`, `blame` на уровне «кто и когда изменил».

Не входит (цель с этим — вне основы, предложить ближайшую внутри):

- администрирование Git-серверов, GitLab и Bitbucket как платформы, настройка CI/CD и GitHub Actions;
- внутреннее устройство Git (объекты, packfiles), `filter-repo`, переписывание большой истории;
- интерактивный rebase сложной истории, `cherry-pick` серий, подмодули, `worktree`, LFS;
- стратегии ветвления больших команд (Git Flow целиком), монорепозитории;
- графические клиенты как основной инструмент;
- программирование: задания не требуют писать код сложнее текстовых файлов.

Ближайшие цели внутри основы:

| Запрос | Ближайшая цель |
|---|---|
| «Хочу настроить CI» | отправлять изменения через ветку и pull request и отвечать на ревью |
| «Хочу разобраться в rebase» | понимать историю веток, сливать их через merge и разрешать конфликты |
| «Хочу работать в команде» | вести свою ветку, синхронизироваться с удалённым репозиторием, открывать PR |

## Карта компетенций

Уровни: **начальный** — выполняет команду по подсказке; **базовый** — выбирает команду под типовую ситуацию; **уверенный** — понимает состояние репозитория по `status` и `log` и исправляет нестандартную ситуацию.

| № | Компетенция | Опирается на |
|---|---|---|
| G1 | Модель Git: рабочая копия, индекс, история | — |
| G2 | Коммиты и чтение истории | G1 |
| G3 | `.gitignore` и чистота репозитория | G2 |
| G4 | Ветки и слияние | G2 |
| G5 | Конфликты слияния | G4 |
| G6 | Откат и исправление изменений | G2, G4 |
| G7 | Удалённый репозиторий | G2, G4 |
| G8 | Pull request и ревью | G4, G7 |

### G1. Модель Git

Объясняет три области: рабочая копия, индекс (staging), история коммитов; понимает вывод `git status`.
Критерий освоения: по выводу `status` говорит, какие изменения войдут в следующий коммит.

### G2. Коммиты и история

Делает коммиты выборочно (`add` конкретных файлов), пишет понятные сообщения, смотрит `log`, `diff`, `show`.
Критерий: история задания состоит из нескольких логичных коммитов с осмысленными сообщениями; находит в истории коммит, где изменилась строка.

### G3. `.gitignore`

Понимает, что не должно попадать в репозиторий (секреты, артефакты сборки, виртуальное окружение, файлы ОС), пишет шаблоны, убирает из индекса случайно добавленный файл (`git rm --cached`).
Критерий: в репозитории нет игнорируемых файлов, `.gitignore` их покрывает.

### G4. Ветки и слияние

Создаёт ветку под задачу, переключается, сливает в основную; различает fast-forward и merge-коммит.
Критерий: изменения сделаны в отдельной ветке и влиты в основную, история это показывает.

### G5. Конфликты

Понимает, почему возник конфликт, читает маркеры `<<<<<<<`, `=======`, `>>>>>>>`, выбирает итоговое содержимое, завершает слияние.
Критерий: конфликт разрешён осмысленно (сохранены нужные изменения обеих сторон), маркеров в файлах нет, слияние закоммичено.

### G6. Откат изменений

Выбирает инструмент: отменить правку в файле (`restore`), убрать из индекса, исправить последний коммит (`--amend`), отменить опубликованный коммит новым (`revert`); понимает, почему нельзя переписывать опубликованную историю.
Критерий: ошибочное изменение отменено способом, подходящим к ситуации, без потери чужой работы.

### G7. Удалённый репозиторий

Клонирует, отправляет ветку, забирает изменения, понимает «ahead/behind», решает отказ `push` из-за новых коммитов на сервере.
Критерий: ветка отправлена на сервер; локальная ветка синхронизирована после изменений на сервере.

### G8. Pull request и ревью

Открывает PR из своей ветки, описывает изменения, отвечает на замечания новыми коммитами в ту же ветку.
Критерий: замечания ревью исправлены коммитами в ветке PR, PR слит.

## Примеры заданий

Встроенные вопросы:

- выбор одного: «Что сделает `git add file.txt`?» — добавит изменения файла в индекс; отвлекающие: создаст коммит, отправит на сервер;
- выбор нескольких: «Что стоит добавить в `.gitignore`?» — `.env`, `__pycache__/`, `venv/`; отвлекающие: `README.md`, исходный код;
- короткий ответ: «Чем `revert` отличается от `reset`?» — критерий: `revert` создаёт новый коммит, отменяющий изменения, и не переписывает историю; `reset` перемещает ветку и меняет историю.

Практика (в учебном репозитории, проверка по истории):

- оформить заготовку проекта тремя логичными коммитами с понятными сообщениями;
- добавить `.gitignore` и убрать из репозитория случайно закоммиченный `.env`;
- сделать изменение в ветке `feature/greeting` и слить его в `main`;
- разрешить подготовленный конфликт в `config.txt`, сохранив изменения обеих веток;
- отменить ошибочный опубликованный коммит через `revert`.

Экзамен (два варианта):

- вариант А: в ветке добавить файл и исправить подготовленную ошибку, разрешить конфликт с `main`, в истории — revert ошибочного коммита, нет игнорируемых файлов;
- вариант Б: те же навыки на другой ситуации: две ветки с правками одного документа, конфликт, отмена коммита с лишним файлом, `.gitignore`.

## Цель по умолчанию и типовой план

Цель «основы Git»: **вести историю проекта коммитами и ветками, разрешать конфликты, отменять ошибки и сдавать работу через pull request.**

Типовой план:

1. **Как устроен Git** — рабочая копия, индекс, история, `status` (G1).
2. **Коммиты и история** (G2, G3). Практика: коммиты и `.gitignore`.
3. **Ветки и слияние** (G4). Практика: ветка и merge.
4. **Конфликты** (G5). Практика: разрешить конфликт.
5. **Исправление ошибок** (G6). Практика: revert и amend.
6. **Работа с GitHub** (G7, G8). Практика: push и PR с ответом на ревью.

Все задания сдаются через PR в учебном репозитории, поэтому G7 и G8 в начальном виде нужны с первой практики: в модуле 2 ученик делает первый push по инструкции, глубже — в модуле 6.

## Типичные ошибки новичков

- `git add .` добавляет всё подряд, включая `.env` и артефакты; секреты попадают в историю.
- Коммит «fix» или «изменения» без смысла; один огромный коммит на всё.
- Работа прямо в `main`, а не в ветке; забыл переключиться на нужную ветку перед правками.
- Оставленные маркеры конфликта в файле; разрешение конфликта, при котором теряются изменения одной из сторон.
- `reset --hard` с потерей незакоммиченной работы; переписывание опубликованной истории и `push --force`.
- Путает `pull` и `fetch`; не понимает отказ `push` из-за новых коммитов на сервере.
- Считает, что `.gitignore` удаляет уже закоммиченные файлы из репозитория.
- Новый PR на каждое исправление вместо коммита в ту же ветку.
