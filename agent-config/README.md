# Инструкции агентов ai-tutor

Здесь лежат рабочие инструкции пяти ролей и экспертная основа трёх направлений: Python, Git, Project Management. Бизнес-логика их не содержит: поменять поведение агента можно правкой этих файлов, без изменения кода. Термины — по [GLOSSARY.md](../GLOSSARY.md), решения — [ADR-0003](../docs/adr/0003-codex-runtime.md) и [технические решения](../docs/implementation-decisions.md).

## Как файлы попадают к агенту

- Compose монтирует `./agent-config` в контейнер бэкенда только для чтения.
- При старте **каждой новой сессии** агента бэкенд читает файлы заново и собирает developer instructions:
  - роли без направления — `roles/<role>.md`;
  - роли направления — `roles/<role>.md`, затем `directions/<direction>/base.md`.
- Структурированный ответ задаётся `outputSchema` из [`contracts/agent-result.schema.json`](../contracts/agent-result.schema.json). Промпт объясняет смысл полей, а формат JSON обеспечивает схема. Ответ, не прошедший схему, — ошибка операции, а не одобрение и не зачёт.
- Модель роли задаётся переменной окружения `MODEL_<ROLE>`. Значения по умолчанию — в техническом решении.

## Роли

| Роль | Файл | Направление в инструкциях | Модель | Вход | Выход (`kind`) |
|---|---|---|---|---|---|
| Наставник-планировщик | `roles/planner.md` | да | `MODEL_PLANNER` | сообщения ученика и служебные сообщения `[…]` | `interview_turn`, `plan_proposal` |
| Ревьюер плана | `roles/plan-reviewer.md` | да | `MODEL_PLAN_REVIEWER` | JSON `{direction, goal, profile, plan}` | `plan_review` |
| Генератор курса | `roles/generator.md` | да (+ `input/base.md` в папке) | `MODEL_GENERATOR` | рабочая папка `/workspace/input` | файлы в `/workspace/out`, короткий итог текстом |
| Учебный наставник | `roles/learning-mentor.md` | да | `MODEL_LEARNING_MENTOR` | сообщение ученика + блок `[Контекст]`, папка `/course` | текст ученику |
| Ревьюер работ | `roles/work-reviewer.md` | да | `MODEL_WORK_REVIEWER` | JSON с полем `mode` | `work_review`, `content_review` |

### Наставник-планировщик

Ведёт интервью, составляет план, обсуждает его с учеником до подтверждения. Одна сессия на курс: интервью, план, исправления по замечаниям ревьюера, обсуждение. Служебные сообщения бэкенда: `[Начало интервью]`, `[Ученик пропустил интервью]`, `[Составь план]`, `[Ревьюер плана] …`. Про ревьюера ученику не говорит.

### Ревьюер плана

Отдельный запрос без истории интервью: проверяет цель (три мягких критерия) и план по карте компетенций. `approved` только при отсутствии замечаний. Ответы ученика не оценивает.

### Генератор курса

Новая чистая сессия после подтверждения плана. Видит только утверждённый пакет в `/workspace/input`, истории интервью нет. Пишет версию курса в `/workspace/out`: публичную часть, служебную часть, официальные проверки и файлы учебного репозитория. Бэкенд валидирует результат (`backend/internal/course`) и отдаёт его Ревьюеру работ; при ошибках структуры или замечаниях ревьюера присылает их следующим ходом той же сессии (`[Проверка структуры] …`, `[Ревьюер работ] …`), и Генератор исправляет `out/`.

### Учебный наставник

Чат на странице курса. Материалы — в `/course`, смонтированной только для чтения: `course.json` и `pages/*.md`. Туда попадает только публичная часть версии. Профиль, текущая страница и прогресс приходят в каждом сообщении блоком `[Контекст]`.

### Ревьюер работ

Одна роль направления в нескольких режимах (`mode`): `short_answer`, `case`, `code`, `content_review`. Каждый запрос отдельный, без контекста других работ. Флаг `exam: true` запрещает подсказки.

## Экспертная основа

`directions/<direction>/base.md`: границы направления, карта компетенций с уровнями и связями, критерии освоения, примеры заданий, цель по умолчанию и типовой план, типичные ошибки. Основа задаёт, какие цели принимаются: цель вне основы Наставник заменяет ближайшей внутри или курс не создаётся.

## Как изменить

1. Отредактируйте нужный файл и закоммитьте его.
2. Новые сессии получат изменения сразу: перезапуск и пересборка не нужны. Уже идущая сессия планирования продолжает со старыми инструкциями, они зафиксированы при её старте.
3. Перед изменением критериев оценивания прогоните `make test-assessment`, после — `make eval-live` по [протоколу качества](../evals/protocol.md). Пороги протокола при этом не меняются.

## Чего нельзя

- Класть правильные ответы, подсказки, разборы, критерии и официальные тесты в материалы, доступные ученику или Учебному наставнику. Они живут только в служебной части версии курса.
- Просить модель вернуть «зачёт», если вызов не удался: ошибка и тайм-аут — ошибка, а не результат.
- Писать в инструкции секреты, ключи и данные конкретных учеников.
- Менять протокол входов и выходов только здесь: он согласован с кодом и схемами в `contracts/`.
