# Отдельный сайт для PoC персонального Наставника

PoC должен быть отдельным сайтом для самостоятельного обучения, а не Claude-плагином. Основной пользователь — ученик со своей учебной целью; потенциальные участники включают родственников автора и добровольцев среди студентов. Решение меняет целевую модель продукта и заменяет ADR-0001; существующий плагин остаётся ранним прототипом, а не реализацией нового решения.

## Рассмотренные варианты

- Сохранить Claude-плагин: позволяет использовать существующий прототип и быстрее начать проверку обучения.
- Создать отдельный сайт: выбран пользователем как необходимый формат доступа для учеников, несмотря на дополнительную работу по созданию сервиса.

Интерфейс реализуется на React, бэкенд — на Go; пользователь хочет освоить Go в ходе работы над проектом. Выбрана интеграция с GitHub. Требуются метрики Prometheus, панели Grafana, логи и трейсы. Выбраны модели OpenAI и локальный Codex app-server как движок агента; разделение сессий и открытый вопрос авторизации сервиса описаны в [ADR-0003](0003-codex-runtime.md). Доступ к учебным репозиториям выдаётся через приглашение подключённого GitHub-аккаунта; конкретная организация и технический механизм авторизации интеграции пока не выбраны.

## Согласованные границы PoC

- 25 октября 2026 года пользователь утвердил [макеты ai-tutor](../prototypes/README.md): тёмный минималистичный интерфейс, главная с наставниками без левого сайдбара, интервью в чате, раскрываемый план, подтверждение и генерация курса. В курсе вопросы встроены в постраничную теорию без отдельной вкладки «Тест»; чат находится сбоку. Детали отражены в AC-04 инженерной приёмки. Утверждение макетов не означает готовность приложения или автоматической оценки.

- Помимо двух показателей посещаемости требуются технические метрики: запросы, коды ответов, ошибки (включая 5xx), задержки и состояние приложения. Они собираются Prometheus и отображаются в Grafana; конкретные проверки перечислены в чек-листе приёмки. Логи и трейсы также должны быть доступны в локальном окружении.
- Приложение не ограничивает число отправок решений и запусков CI. Правило первой и второй ошибки управляет выдачей помощи, а не количеством разрешённых попыток.
- Для завершения реализации достаточно воспроизводимого локального запуска. Публикация в интернете не обязательна. Авторизация проверяется с локальным тестовым почтовым ящиком; реальная доставка писем не требуется.
- Учебные репозитории размещаются в отдельной GitHub-организации платформы: один приватный репозиторий на курс ученика. Ученику выдаётся доступ к своему репозиторию для отправки решений, но не к репозиториям других учеников.
- Для Python и Git ученик подключает свой GitHub-аккаунт после подтверждения плана, перед подготовкой курса; это блокирующий шаг, генерация не начинается до подключения. После создания репозитория система приглашает туда подключённого пользователя; сайт показывает ссылку принятия приглашения. После принятия доступны ссылка на репозиторий и инструкция клонирования и отправки решения. Вход на сайт остаётся по одноразовому коду из почты; для Project Management подключение GitHub не требуется.
- Должен быть подготовлен шаблон учебного репозитория, который агент использует как основу при генерации репозитория курса.
- Ученик может иметь несколько курсов, в том числе по одному направлению; у каждого курса Python или Git свой репозиторий. Лимит незавершённых курсов не вводится.
- Курс считается полностью готовым, когда сгенерированы теория, предусмотренная планом практика и два варианта итогового экзамена. Если практики в плане нет, достаточно теории и экзамена; сбой генерации предусмотренной практики не превращает курс в теоретический. Согласованные ревью и сохранение материалов перед публикацией сохраняются. Принятие GitHub-приглашения учеником отражает готовность доступа к практике отдельно от готовности содержимого курса.
- Если материалы готовы, а подготовка репозитория завершилась ошибкой, сайт показывает ошибку и кнопку «Повторить». Повторяется подготовка репозитория без повторной генерации материалов; сначала система проверяет, не был ли репозиторий уже создан, и использует существующий, чтобы избежать дубликата.
- При техническом сбое генерации курса PoC показывает ошибку и кнопку «Повторить»; автоматический перезапуск генерации не требуется. Ученик запускает повтор по сохранённому подтверждённому плану, без повторного интервью. Повтор не должен создавать второй репозиторий того же курса. Это правило относится к техническому сбою, а не к согласованному циклу исправлений по замечаниям ревьюера.
- Репозиторий ученика предназначен для практики: условия, заготовки кода, решения и инструкция локального запуска. Теория остаётся в S3. Официальные проверки платформа хранит отдельно от репозитория ученика и запускает на отправленной версии решения. Примеры тестов для локальной тренировки допустимы, но их изменение не подменяет официальные проверки и не даёт зачёт. Это уточняет прежнюю схему размещения материалов и проверок в одном учебном репозитории.
- Пока план готовится, ученик видит этапы «Составляем план», «Проверяем план», «Вносим исправления». План открывается для обсуждения после одобрения Ревьюером плана.
- Ученик выбирает наставника и цель, обсуждает предложенный план в диалоге и явно подтверждает его итоговую версию. Для Python и Git после подтверждения создаётся персональный учебный репозиторий.
- Страница курса объединяет план, теорию, задания, прогресс и чат с тем же Наставником. Теория всех направлений хранится в S3 в составе версии курса и отображается на сайте; отдельный репозиторий теории не создаётся. В интервью можно определить предпочтения общения.
- Интеграция с GitHub связывает результат CI с конкретной отправкой решения. После push ученик видит ожидание или выполнение проверки. Ошибка обозначается красным крестиком, текстом и краткими деталями, со ссылкой на соответствующий запуск CI в GitHub. Результат официальной проверки публикуется как check run на коммите ученика через GitHub Checks API; ссылка ведёт на него, доступ к инфраструктуре проверок ученику не выдаётся. Успех CI обозначается зелёной галочкой и текстом. Для зачёта работы с кодом дополнительно требуется одобрение Ревьюером работ той же версии решения. Полный журнал CI на странице курса не требуется.
- Преподаватель видит список учеников, их цели и прогресс и открывает страницу курса в режиме просмотра. Доступны история интервью, все задания, ответы, попытки, оценки и чат. Отдельный аналитический раздел не требуется. Роль — флаг на аккаунте: при старте приложение создаёт аккаунт из `ADMIN_EMAIL`, вход тем же одноразовым кодом, пароля нет; флаг можно выдать командой позже. Преподаватели не учитываются в посещаемости.
- Промпты, карта навыков и критерии хранятся в файлах репозитория приложения. Редактор экспертных материалов на сайте не входит в PoC.
- Если для хранения данных выбирается реляционная БД, предпочтение пользователя — PostgreSQL. Для локального PoC отдельный внешний сервер БД не требуется.
- Выбор технических компонентов и подготовка автоматических проверок качества поручены агенту-разработчику. Он документирует решения и проверяет их по инженерной приёмке, без обязательной ручной разметки пользователем. Рутинные технические вопросы решает самостоятельно; у пользователя запрашивает необходимые доступы. Методика и пороги качества фиксируются до итогового прогона, фактические результаты и ограничения сохраняются в отчёте.
- Ручное редактирование сгенерированных курсов и критериев заданий преподавателем или администратором отложено за пределы PoC. Кабинет преподавателя остаётся в режиме просмотра; отдельный интерфейс вмешательства суперпользователя не требуется. Это не отменяет настройку экспертной основы в файлах репозитория приложения.
- Регистрация открыта: начать обучение можно без приглашения и списка разрешённых адресов.
- Вход по почте с одноразовым кодом; постоянного пароля нет. Сессия сохраняется между посещениями, поэтому новый код не требуется при каждом открытии сайта.
- Оспаривание оценки и отдельный процесс повторной проверки по жалобе ученика в PoC не входят. Это не отменяет обычных учебных попыток и повторного экзамена после повторения материала.
- Направления: Python, Git и основы Project Management. MLOps остаётся возможным будущим направлением; в PoC не входит.
- Наличие практики определяется подтверждённым планом курса; допускается курс без практики. Это заменяет прежнее требование обязательной практики в каждом курсе. Поддерживаются только цели в пределах экспертной основы, для которых можно обеспечить надёжную проверку.
- Агент-разработчик в ходе реализации готовит первые версии инструкций для всех согласованных ролей: промпты, необходимые скиллы и начальные экспертные материалы по Python, Git и Project Management. Они хранятся в файлах репозитория приложения; пользователь может корректировать их по необходимости. Предварительная подготовка или обязательное утверждение этих файлов пользователем не блокирует реализацию. Обязательная ручная разметка контрольных работ или проверка сгенерированных материалов автором не входит в цепочку подготовки и прохождения курса. Это уточнение заменяет прежнее требование подготовки экспертной основы автором до реализации и предварительной ручной проверки примеров.
- Отдельный Ревьюер плана автоматически проверяет учебную цель и учебный маршрут Наставника по заданным критериям и возвращает ему замечания для исправления. Критерии цели мягкие: понятный результат, проверяемость, реалистичный объём. Наставник уточняет цель с учеником столько, сколько нужно, предлагая понятные варианты; цель вне экспертной основы заменяется ближайшей внутри основы или курс не создаётся. Ревьюер плана не оценивает ответы ученика. Обязательного участия преподавателя в этом цикле нет. Ученик обсуждает и подтверждает уже прошедший ревью план; изменения содержания по итогам обсуждения повторно проходят ревью.
- Индивидуальный план сохраняется. Изменение маршрута по ошибкам отложено. Правило «первая ошибка — подсказка, вторая — разбор» действует только для встроенных вопросов; подсказку и разбор создаёт Генератор вместе с вопросом. Для кода и кейсов автоматических подсказок и готовых решений нет: Ревьюер работ пишет замечания по критериям, за помощью ученик обращается к Наставнику сам. Учёт прохождения «с помощью» в PoC не ведётся; самостоятельное освоение проверяется на экзамене.
- Итоговый экзамен содержит новые задания по изученным навыкам. Генератор создаёт два варианта в составе версии курса, оба проходят ревью до публикации. Экзамен доступен сразу после готовности курса. Сдач не больше двух, интерфейс показывает лимит. После первой неудачи ученик видит невыполненные требования, может повторить материал и сдать второй вариант. После второй неудачи курс получает статус «экзамен не сдан», новый курс начинается с интервью. Курс завершён после зачёта экзамена.
- Перед составлением плана Наставник проводит уточняющее интервью в формате grilling: задаёт вопросы об учебной цели и исходной подготовке. Отдельный обязательный стартовый тест не выбран. Интервью можно пропустить и начать с нуля. Оценка уровня по интервью остаётся предварительной.
- Проверки работ автоматизированы. Практику Python и Git ученик выполняет на своём компьютере и отправляет в учебный репозиторий; настройка окружения входит в подготовку. Сайт показывает задания, результаты CI-проверок и обратную связь. Итоговые проверки контролирует система; техническая реализация ещё не определена.
- Работы по Project Management ученик сдаёт непосредственно на сайте; Git для этого направления не требуется. Их проверяет отдельный Ревьюер работ направления Project Management, возвращает обратную связь и решение о зачёте либо необходимости исправлений.
- Для Python и Git ученик сдаёт решение через pull request в учебном репозитории. Ревьюер работ проверяет изменения по критериям задания, оставляет комментарии в GitHub и оформляет approve либо запрос исправлений. Зачёт требует успешного CI и одобрения ревьюера для одной версии решения. Новый коммит требует актуальных результатов проверок и ревью; старое одобрение не засчитывает изменённый код. Это уточнение заменяет прежний зачёт только по зелёному CI. Ревьюер плана остаётся отдельной ролью.
- Ревью работ выполняется автоматически без обязательного участия преподавателя. Ревьюер запускается на каждый коммит в PR независимо от CI; комментарии указывают невыполненные критерии и не содержат готового решения ни в обучении, ни в экзамене. Approve возможен только при успешной официальной проверке той же версии. После успешного CI и approve для текущей версии система автоматически объединяет pull request; ученику не нужно нажимать Merge. При конфликте или ошибке GitHub объединение не отображается как выполненное; результат проверки работы и состояние merge различаются.
- Для основ Project Management итог включает тестирование знаний и практический кейс: цель проекта, задачи, последовательность и сроки, риски, затем корректировку плана при изменении условий. Обе части требуют отдельного зачёта. Способ автоматической проверки качества оценивания кейса ещё требуется определить; ревью учебного плана само по себе его не подтверждает.
- Платежи и проверка готовности платить исключены из PoC.
- Желаемый результат — самостоятельное продолжение занятий без личных напоминаний автора. На старте отслеживаются только два показателя посещаемости: всего уникальных учеников, хотя бы раз посетивших платформу, и регулярно активные ученики, посетившие её минимум в два разных дня за последние семь дней.
- Посещение — любой аутентифицированный запрос ученика к серверу. В БД сохраняется история посещений с идентификатором ученика и временем визита, а не только последняя дата входа.
- Для локальной приёмки Codex app-server авторизуется ключом API OpenAI с лимитом расходов; личная подписка использовалась только в спайке. Повторные посещения и обновления страницы не увеличивают число уникальных учеников. Учебный прогресс и результаты экзаменов сохраняются отдельно.
- Конкретные темы сейчас не фиксируются. Эксперт позднее определяет поддерживаемые навыки и критерии проверки; Наставник выбирает нужную часть по цели и исходной подготовке ученика. Общий фиксированный курс для всех не требуется.

## Последствия и открытые вопросы

PoC предназначен для проверки пользы индивидуального плана, практики и обратной связи. Выбранные показатели посещаемости описывают использование платформы; сами по себе они не подтверждают освоение навыков или самостоятельность занятий. Польза адаптации маршрута и коммерческий спрос в этом PoC не проверяются.

Предполагаемая первая аудитория Python — начинающие с базовыми знаниями и пробелами. Конкретные области Python и Git, цели участников, содержание диагностического интервью, пороги зачёта, допустимые ошибки автоматического оценивания ещё не согласованы. Пороги привлечения и удержания пользователей не назначаются: пользователь запросил критерии завершения реализации для агента, а не условия успеха рыночного эксперимента. API использовались только как пример области обучения.

Голос, аватары и большой каталог профессий остаются за пределами первой версии.

Критерии завершения реализации обсуждаются отдельно: [проект инженерной приёмки](../poc-acceptance.md).
