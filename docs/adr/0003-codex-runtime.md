# Codex app-server как движок Наставника

Для PoC выбираем готовый Codex в контейнере с управлением через app-server вместо разработки собственного цикла агента. Go-бэкенд отвечает за учеников, права доступа, прогресс и orchestration; Codex — за диалог и выполнение задач подготовки курса. Выбор предварительно проверяется небольшим локальным экспериментом, а не считается доказанной интеграцией всего сервиса.

Интервью и согласование плана выполняются в одной сессии на более сильной модели OpenAI. Генерация материалов и заданий начинается после подтверждения в новой сессии с чистым контекстом. Она получает утверждённые цель, исходные условия и план, экспертную основу, нужные скиллы и шаблон; исходная история интервью не переносится. Конкретные модели задаются конфигурацией по этапам. Модели учебного чата и оценивания ещё не выбраны.

Согласованы пять ролей: Наставник-планировщик, Ревьюер плана, Генератор курса, Учебный наставник и Ревьюер работ соответствующего направления. Это разделение обязанностей, а не требование пяти постоянно работающих контейнеров.

Генератор курса получает рабочую папку для создания материалов, заданий и проверок по подтверждённому плану. После завершения генерации Go-бэкенд сохраняет результат и делает курс доступным ученику. Здесь публикация означает доступность курса внутри приложения и размещение учебного репозитория согласно выбранной схеме, а не открытие материалов в публичный доступ. Точный формат результата генератора и обязательные проверки перед публикацией ещё предстоит определить.

Согласована структура содержимого: оглавление с модулями и страницами; страница — упорядоченный список блоков Markdown и встроенных вопросов. Генератор определяет содержание и порядок, React отображает блоки в заданном интерфейсе. Правильные ответы и правила проверки отделены от доступных ученику материалов. Точная схема файлов и валидация пока не выбраны; см. [формат курса](../course-format.md).

Критерии зачёта конкретного задания Генератор курса создаёт вместе с заданием на основе экспертных правил направления. Обязательное ручное описание критериев каждого задания пользователем не требуется. Ревьюер работ применяет критерии соответствующего задания при проверке решения.

До публикации курса тот же Ревьюер работ соответствующего направления проверяет задания и критерии отдельным запросом. Генератор исправляет замечания, после чего обновлённый результат снова проходит ревью. Бэкенд делает курс доступным ученику после одобрения актуальной версии. Обязательного ручного участия пользователя нет. Эта проверка отличается от ревью плана и от проверки ответов ученика; новая роль не вводится. Механизм измерения качества такого ревью остаётся открытым вопросом.

Постоянное хранение версий курса — S3-совместимое объектное хранилище. Генератор создаёт результат в рабочей папке, затем Go-бэкенд загружает готовую версию в хранилище и сохраняет ссылку на неё в БД. Прогресс, ответы и история обучения остаются в БД. Перед запуском Учебного наставника бэкенд скачивает материалы выбранной версии в локальную папку и подключает её к контейнеру только для чтения. Локальная папка — восстанавливаемая копия, а не единственное постоянное хранилище курса. В неё попадают только материалы, доступные ученику; служебные ответы и скрытые проверки не скачиваются для Учебного наставника.

S3-совместимое хранилище можно запускать локально в Docker в соответствии с выбранной локальной приёмкой PoC. Конкретный продукт ещё не выбран. В приватной GitHub-организации размещается только репозиторий практики Python и Git; теория остаётся в S3 без отдельного репозитория, официальные проверки хранятся отдельно под управлением платформы; курс на сайте и локальная копия агента должны соответствовать одной сохранённой версии. Точный механизм согласования версии с репозиторием предстоит определить.

Учебный чат работает в отдельной сессии, отличной от планирования и генерации. При старте он получает краткий профиль ученика и путь к текущей странице. Go-бэкенд добавляет актуальные прогресс, попытки и результаты проверок в контекст сообщений; история учебного диалога сохраняется отдельно от подготовительных сессий.

Для чтения курса в PoC выбираем файловый доступ: к контейнеру Учебного наставника подключается папка конкретного курса только для чтения. Она содержит оглавление, страницы материала и условия заданий, доступные ученику. Агент читает нужные файлы инструментами Codex; весь курс не требуется заранее помещать в контекст. Скрытые проверки, готовые решения и материалы других учеников в эту папку не включаются. Это подготовленный набор учебных файлов, а не полный checkout со служебными файлами и историей Git. Для Project Management также формируется папка материалов; GitHub для этого направления не требуется.

MCP-интерфейс получения материалов через Go-бэкенд обсуждался как альтернатива и не выбран для PoC: файловая структура уже соответствует результату генерации и не требует отдельного интерфейса чтения. Решение относится к доступу Учебного наставника к материалам, а не к способу работы всех интеграций. Реализация и изоляция такого доступа ещё должны пройти приёмку.

План Наставника проверяет отдельный агент-ревьюер с заданными промптом и критериями. Замечания возвращаются Наставнику для исправления без обязательного участия человека. Ревью решений ученика этой роли не поручается. Ученик получает для обсуждения и подтверждения уже прошедший ревью план. Если при обсуждении меняется содержание плана, изменённая версия снова проходит ревью перед подтверждением и генерацией курса. В PoC нет ограничения количества циклов ревью и исправлений: Наставник продолжает исправления до одобрения Ревьюером плана. Пользователь отложил ограничение циклов до появления реальной проблемы; остановка после трёх или иного заданного числа циклов не требуется.

Решения учеников проверяет отдельный Ревьюер работ соответствующего направления. Для Project Management он оценивает ответы на сайте; для Python и Git проверяет pull request, публикует комментарии и approve либо запрос исправлений. Зачёт кода требует успешного CI и одобрения ревьюера для той же версии. После выполнения этих условий система автоматически объединяет pull request; отдельного действия ученика для merge не требуется. Модели и организация сессий Ревьюеров работ ещё не выбраны.

Короткие текстовые ответы во встроенных заданиях также проверяет Ревьюер работ соответствующего направления. Новая роль для этого не создаётся: используются отдельные запросы с инструкциями для вида задания. Для текстового ответа входом служат вопрос, критерии и ответ ученика; для PR — задание, код и результаты CI. Проверка текста учитывает смысл и критерии, допускает верные формулировки своими словами и возвращает зачёт либо замечания. Контекст разных работ не смешивается; Ревьюер плана не участвует в оценивании ответов ученика.

Для локального технического эксперимента пользователь разрешил использовать собственную подписку ChatGPT. Авторизация будущего размещённого сервиса остаётся открытым решением между API и отдельным механизмом Sign in with ChatGPT после проверки доступности и условий. Личная авторизация app-server не становится общим доступом для учеников.

Собственный движок отложен: он потребовал бы отдельно реализовать работу с инструментами, контекстом, событиями и сессиями. Управляемый Agents API не выбран; его нельзя смешивать с локальным процессом codex app-server. Версию Codex следует фиксировать, протокол проверять на этой версии. Технический эксперимент не подтверждает качество обучения, оценивания или готовность к эксплуатации.

Основание: [app-server](https://learn.chatgpt.com/docs/app-server), [авторизация](https://learn.chatgpt.com/docs/auth). Скрипт локальной проверки: [run.py](../research/codex-runtime-spike/run.py).
