# ai-tutor PoC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Реализовать локальный сервис обучения по персональному плану и подтвердить AC-01…AC-14 воспроизводимыми проверками.

**Architecture:** React-интерфейс и Go-бэкенд управляют пользователями, курсами и заданиями. Codex app-server работает в контейнерах с раздельными сессиями по ролям; версии курса хранятся в S3, история и прогресс — в БД. GitHub содержит приватные репозитории практики; официальные проверки выполняются под управлением платформы отдельно от изменяемых учеником файлов.

**Tech Stack:** React, Go, Codex app-server, модели OpenAI, S3-совместимое хранилище, GitHub, Prometheus, Grafana. Конкретные библиотеки, БД и остальные компоненты выбирает исполнитель в задаче 1.

Уточнение пользователя от 26 октября: при выборе реляционной БД предпочесть PostgreSQL.

**Spec:** [Приёмка](../../poc-acceptance.md), [ADR-0002](../../adr/0002-otdelnyj-sajt-dlya-poc.md), [ADR-0003](../../adr/0003-codex-runtime.md), [формат курса](../../course-format.md), [утверждённые макеты](../../prototypes/README.md).

## Global Constraints

- Источник требований — перечисленные документы; спецификация от 24 октября и Claude-плагин исторические. Не переносить из них оплату, закрытую регистрацию или адаптацию маршрута.
- Достаточно локального запуска. Вход по коду из локального тестового почтового ящика; постоянного пароля нет.
- Python, Git и Project Management. Первые рабочие инструкции, скиллы и экспертную основу готовит исполнитель; обязательного утверждения пользователем нет.
- Теория — в S3, практика Python/Git — в приватной GitHub-организации. Официальные тесты и ответы отделены от файлов ученика и Учебного наставника.
- Генератор получает чистую сессию и утверждённые входы. Учебный чат — отдельная сессия с папкой материалов только для чтения; MCP для чтения курса не нужен.
- После технического сбоя генерации — ошибка и ручной повтор. Не вводить автоматический повтор генерации или лимит циклов содержательного ревью плана.
- Курс готов после генерации теории и предусмотренной планом практики, ревью и сохранения. Для плана без практики достаточно теории. Доступ к GitHub отслеживается отдельно.
- Нет лимита учебных попыток. Правило «первая ошибка — подсказка, вторая — разбор» только для встроенных вопросов, подсказку и разбор создаёт Генератор. Для кода и кейсов подсказок нет, Ревьюер работ не выдаёт готовое решение. Учёт «с помощью» не ведётся. Экзамен: два варианта в версии курса, не больше двух сдач, без подсказок.
- Преподаватель — флаг на аккаунте из `ADMIN_EMAIL` при старте, вход по коду без пароля. Ученик может иметь несколько курсов. Подключение GitHub — блокирующий шаг перед генерацией. Codex авторизуется ключом API.
- Код засчитывается по успешным официальным проверкам и approve текущей версии; merge автоматический. Ошибка merge не изображается как успех.
- Кабинет преподавателя только для просмотра. Редактирование курсов, критериев и прогресса через админ-интерфейс отложено.
- Не изменять пользовательские незакоммиченные файлы вне задачи. Не считать старые тесты player доказательством готовности нового сервиса.

## Review Focus

- Старые или повторные события CI/review не меняют результат новой отправки — задача 6.
- Потеря ответа после создания репозитория не создаёт второй репозиторий при повторе — задача 6.
- Смена курса, ученика или версии не открывает чужие материалы и служебные ответы — задачи 2, 4, 5.
- Перезапуск приложения не теряет подтверждённый план, попытки и историю — задачи 3, 5, 9.
- Изменение тестов или workflow учеником не подменяет официальную оценку — задача 6.

## Порядок и структура

Работать последовательно; задачи 2–8 дают проверяемые части сервиса. Это общий план нескольких подсистем: после выбора компонентов исполнитель детализирует ближайшую задачу конкретными типами и тестами, не требуя от пользователя выбора библиотек.

Предлагаемые новые каталоги (существующий `player/` сохраняется):

| Путь | Ответственность |
|---|---|
| `web/` | React-интерфейс и браузерные сценарии |
| `backend/cmd/server/`, `backend/internal/` | HTTP, доменные операции, фоновые работы, интеграции |
| `backend/migrations/` | Схема БД и обновления |
| `contracts/` | OpenAPI, схемы курса и результатов агентов |
| `agent-config/roles/`, `agent-config/directions/` | Промпты, скиллы, экспертные материалы |
| `templates/practice/` | Основа репозиториев практики |
| `infra/`, `compose.yaml` | Локальные сервисы и наблюдаемость |
| `evals/`, `docs/verification/` | Контрольные наборы, методика и отчёты |

Имена внутренних функций исполнитель определяет после выбора компонентов. Общие границы фиксируются в `contracts/openapi.yaml` и схемах до подключения потребителей; контрактные тесты проверяют совместимость Go и React. Все приведённые ниже команды — целевые команды, которые нужно создать, а не уже существующие инструменты.

### Task 6: GitHub-практика и официальные проверки

**Files:** создать `backend/internal/github/`, `backend/internal/checks/`, `templates/practice/`, `infra/check-runner/`, `web/src/practice/`, `web/e2e/github.spec.ts`.

**Interfaces:** привязка GitHub identity, репозиторий курса, приглашение, PR/commit, официальный результат, ревью и merge имеют отдельные состояния. Обработчики событий повторяемы без дублирования эффекта.

- [ ] Добавить тесты: потеря ответа после создания репозитория; повтор события; старый CI после нового commit; новый commit между approve и merge; конфликт merge; изменение локальных тестов/workflow не даёт официальный зачёт.
- [ ] Реализовать подключение GitHub после подтверждения плана, создание из шаблона, приглашение и проверку доступа. При сбое репозитория сохранять материалы и повторять только его подготовку.
- [ ] Реализовать официальный запуск тестов вне управляемой учеником конфигурации. Код ученика запускается изолированно от ключей платформы; результаты относятся к точному commit и публикуются как check run на нём через Checks API.
- [ ] Реализовать предметное ревью PR на каждый коммит независимо от CI: комментарии по критериям без готового решения, approve только при зелёной официальной проверке, автоматический merge после актуальных успешных проверок. Для PM GitHub не нужен.
- [ ] `make test-github` проверяет обработчики локально. Отдельный `make verify-github-live` и браузер подтверждают реальный приватный репозиторий, права двух учеников, ошибочное/исправленное решение, ревью и merge (AC-03, AC-05). При отсутствии доступов live-проверка явно остаётся непройденной.
